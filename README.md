# go-fleet-charging

车队充电容量预订服务：充电站按离散时段配置可用功率，多辆车跨时段预订充电容量，
支持精确能量核算、容量原子提交、外部请求号幂等、并发争用、抵达前修改/取消、
站点临时降容时的预约调整方案以及持久化。

开发环境：Go 1.23.0，无第三方依赖。

运行测试：

    go test ./...
    go test -race -count=1 ./...   # 含并发竞态检测

## 核心模型与语义

- **半开区间**：所有时间区间一律左闭右开 `[start, end)`。两辆车在整点钟点
  首尾相接时不共享该瞬时点的容量，能量按区间与配置时段的真实相交长度计算，
  不要求整点对齐。
- **精确能量**：内部能量以“功量”W·ns（瓦 × 纳秒时长）做整数运算，
  乘积用自带的 128 位整数存放，全程无浮点、无预算中途取整；
  仅在最后一步用向上取整把功率取整为整数瓦，因此实际交付能量 **恒不少于**
  请求的最低电量（误差 < 1W × 时长），绝不会少给。
  请求能量单位为微瓦时（µWh，`1 Wh = 1_000_000 µWh`，`1 µWh = 3_600_000 W·ns`）。
- **容量约束**：一个计划可跨多个时段分配功率，但每个时间片内所有有效计划的
  分配功率之和不得超过站点容量；车辆离开前累计交付能量必须达到最低电量。
  任一约束不满足则**整体拒绝**——在提交/修改成功落库前不产生任何占用，
  不存在“先占住一部分再说”。
- **幂等**：`request_id` 是外部请求号。
  - 同号同内容重复提交：直接返回原计划（原计划已取消则返回已取消的原计划）；
  - 同号不同内容：返回幂等冲突错误，原计划保持不变。
- **并发**：提交、修改、取消、状态迁移在同一互斥区内“检查 + 落库”串行完成，
  多辆车并发争用同一时段时，只有仍满足全部容量约束的计划组合能提交成功。
- **抵达前修改/取消**：
  - 修改是**原子替换**：先按旧计划之外的占用计算新分配，成功则一次性替换，
    失败则旧计划与旧占用原封不动；
  - 取消立即释放全部占用；重复取消、取消不存在的计划返回状态错误；
  - 当前时间一旦越过到达点，计划自动迁移为 `arrived` 终态并锁定，
    修改/取消与“越过到达点”同时发生时，二者在同一锁下竞争，
    容量不会泄漏，也不会被重复释放。
- **临时降容与预约调整（两步：准备 → 确认）**：站点可用功率临时下降时，
  通过 `PrepareCurtailment` 先形成一份**可确认但不改动任何状态**的调整方案，
  运营方确认后由 `ConfirmCurtailment` 在**同一次落库事务**中把容量变化落实到
  每一笔受影响预约上。调整规则：
  - 容量事件指定半开影响时段与该时段的新功率（必须严格低于原容量）；
    事件只覆盖该时段，时段之外的配置与预约分配保持不变，
    事件窗口必须完整落在已配置供电时段内。
  - **固定功率预约**（`Fixed=true`）在事件时段内的分配功率不允许任何削减；
    仅固定预约之和就超过新容量时，整份方案无法生成（`capacity` 错误）。
  - 可调预约按 **`Priority` 数值从大到小**依次重排（同优先级按创建先后），
    高优先级先占用事件时段内被固定预约让出后的剩余容量；
    被挤出的功率只能改排到该预约在场窗口内事件时段之外的空闲容量上，
    且调整后交付能量**不得低于最低充电需求**，否则整份方案无法生成。
  - 方案为每笔受影响预约记录生成时的**版本号** `FromRevision`；确认时逐笔比对：
    方案生成后只要有任何预约被修改、取消，或有新预约提交、站点被重配，
    整份方案立即失效，确认返回 `conflict` 错误且**原安排不被部分修改**。
    调用方需重新准备方案再确认。抵达锁定（`active→arrived`）不改变版本号，
    车辆到场期间仍可落实降容；已取消的预约会使方案失效。
  - 确认是**全有或全无**：站点时段容量与全部受影响预约在一次原子写入中替换，
    每笔预约版本号加一；持久化失败时内存态同步回滚，方案仍可重试确认。
    确认前后逐时间片“容量 = 已占用 + 剩余”守恒，释放出的容量与重新占用
    一一对应，不会出现超额占用或容量泄漏。方案只保存在内存中，进程重启后
    需重新准备。

## 计划状态

| 状态 | 含义 |
| --- | --- |
| `active` | 已提交、车辆未抵达，占用容量，可修改或取消 |
| `arrived` | 当前时间已越过到达点，占用保留但不可再修改/取消（终态） |
| `cancelled` | 抵达前被取消，占用为零（终态） |

## API 概览

```go
import (
    "context"
    "time"

    fc "github.com/chris64233/go-fleet-charging"
)

store := fc.NewFileStore("data/charging.json") // 或 fc.NewMemoryStore()
svc, err := fc.NewService(store /*, fc.WithClock(myClock)*/)

// 1) 配置站点：两个半开时段的可用功率
svc.ConfigureStation(ctx, fc.StationConfig{
    StationID: "ST-1",
    Segments: []fc.Segment{
        {Start: t10, End: t11, PowerW: 100_000}, // 10:00–11:00，100 kW
        {Start: t11, End: t12, PowerW: 80_000},  // 11:00–12:00，80 kW
    },
})

// 2) 提交计划（request_id 幂等）
plan, err := svc.SubmitPlan(ctx, fc.ChargeRequest{
    RequestID:    "req-20260101-0001",
    StationID:    "ST-1",
    VehicleID:    "VH-7",
    Arrival:      t10,
    Departure:    t12,
    MinEnergyUWh: 50_000_000_000, // 50 kWh
    MaxPowerW:    100_000,        // 单车功率上限 100 kW
})

// 3) 抵达前原子修改（保持同一 request_id）
svc.ModifyPlan(ctx, "req-20260101-0001", fc.PlanModification{ ... })

// 4) 抵达前取消（释放全部占用）
svc.CancelPlan(ctx, "req-20260101-0001")

// 5) 查询单计划 / 逐时段占用
p, _ := svc.GetPlan(ctx, "req-20260101-0001")
rows, _ := svc.Occupancy(ctx, "ST-1", t10, t12)
// rows: [{Start,End, CapacityW, ReservedW, AvailableW} ...]
// 行边界 = 配置时段边界 ∪ 各计划到达/离开边界，保证每行内占用恒定

// 6) 临时降容：先准备调整方案（不改状态），核对后再确认
plan, err := svc.PrepareCurtailment(ctx, fc.CapacityEvent{
    EventID:   "ev-grid-0007",
    StationID: "ST-1",
    Start:     t10,
    End:       t11,
    PowerW:    60_000, // 该小时容量临时降到 60 kW
})
// plan.Items: 每笔受影响预约的 FromRevision 与调整后完整 Allocation
results, err := svc.ConfirmCurtailment(ctx, plan.Token)
// 期间任何预约被修改/取消、有新提交或站点重配 → fc.KindConflict，原安排不变
```

重新配置站点时，若新配置会使任何既有有效计划超额，返回容量错误且旧配置保持不变。

## 持久化

- `MemoryStore`：进程内存储，适合测试。
- `FileStore`：单个 JSON 文件；写入采用“临时文件 + 原子 rename”，
  崩溃时不会出现半截文件。重启后站点配置、计划、占用、幂等记录全部恢复，
  容量约束继续生效。
- 也可实现 `Store` 接口（`Load/Save`）接入数据库；`Save` 要求整体原子替换。

## 错误分类

所有业务错误均为 `*fc.Error`，按 `Kind` 区分，可用 `fc.KindOf(err)` 取类别，
或用 `errors.Is(err, fc.ErrCapacity)` 等哨兵按类别匹配：

| Kind | 触发场景 |
| --- | --- |
| `parameter` | 空 ID、非正能量/负功率、未知站点、配置时段重叠/乱序、查询区间非法 |
| `capacity` | 剩余容量无法在离开前交付最低电量；降配会击穿既有占用；降容后固定预约放不下或可调预约无法满足最低需求 |
| `time` | 到达不早于离开、到达时间已过、窗口未被已配置供电时段完整覆盖 |
| `state` | 计划不存在、重复取消、已取消/已抵达后再修改或取消、确认不存在或已确认的调整方案 |
| `idempotency` | 同一 `request_id` 提交了内容不同的请求 |
| `conflict` | 降容方案生成后预约被修改/取消、出现新提交或站点被重配，方案版本过期，需重新准备 |

## 分配算法

把配置时段边界与窗口边界（以及占用查询时的计划边界）合并成互不重叠的时间片，
逐片求 `剩余功率 = 站点容量 − 其他有效计划占用`；随后按时间从早到晚贪心填充：

1. 当前片可给功率 `min(剩余功率, 单车功率上限)`；
2. 若整片用完仍不够，取整片功率；
3. 若该片足以补足缺口，只取 `ceil(剩余功量 / 本片时长)` 的最小整数功率；
4. 全部时间片用尽仍不足 → 返回容量错误，不写入任何占用。

贪心在“功率上限为常数、可中途任意改变功率”的模型下是最优的：只要存在可行分配，
最早填充策略就一定能找到。

## 降容重排算法

准备降容方案时，先把事件窗口覆盖到配置时段轴上得到新容量，再按以下次序处理预约：

1. **不受影响**的预约（分配与事件窗口无正长度相交）原样保留，作为既定占用；
2. **固定预约**原样保留，先校验它们在新容量下逐片不超额，超额即整单不可行；
3. **可调预约**按优先级降序（同级按创建次序）逐个在新容量上跑与提交相同的贪心
   分配：已处理的高优先级预约计入占用，未处理的低优先级暂记为零；
   某笔预约即使在窗口外空闲时段补能后仍达不到最低电量，整份方案不可行。

由于低优先级预约总是在“高优先级已占满”的剩余容量上分配，最终方案的逐片可行性
是构造性保证的；确认前还会对全部预约做一次逐片容量复核与逐笔能量复核。
确认事务只做“版本比对 + 对象替换”，不再重新调度，因而准备结果与确认结果严格一致。
