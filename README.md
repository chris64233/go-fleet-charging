# go-fleet-charging

车队充电容量预订服务：充电站按离散时段配置可用功率，多辆车跨时段预订充电容量，
支持精确能量核算、容量原子提交、外部请求号幂等、并发争用、抵达前修改/取消、持久化，
以及站点可用功率临时下降时的两阶段预约调整（出方案 → 确认）。

开发环境：Go 1.23.0，无第三方依赖。

运行测试：

    go test ./...
    go test -race -count=1 ./...   # 含并发竞态检测

## 核心模型与语义

- **半开区间**：所有时间区间一律左闭右开 `[start, end)`。两辆车在整点钟点
  首尾相接时不共享该瞬时点的容量，能量按区间与配置时段的真实相交长度计算，
  不要求整点对齐。
- **精确能量**：内部能量以“功量”W·ns（瓦 × 纳秒时长）做整数运算，
  乘积用自带的 128 位整数存放，全程无浮点、无预算中途取整；
  仅在最后一步用向上取整把功率取整为整数瓦，因此实际交付能量 **恒不少于**
  请求的最低电量（误差 < 1W × 时长），绝不会少给。
  请求能量单位为微瓦时（µWh，`1 Wh = 1_000_000 µWh`，`1 µWh = 3_600_000 W·ns`）。
- **容量约束**：一个计划可跨多个时段分配功率，但每个时间片内所有有效计划的
  分配功率之和不得超过站点容量；车辆离开前累计交付能量必须达到最低电量。
  任一约束不满足则**整体拒绝**——在提交/修改成功落库前不产生任何占用，
  不存在“先占住一部分再说”。
- **幂等**：`request_id` 是外部请求号。
  - 同号同内容重复提交：直接返回原计划（原计划已取消则返回已取消的原计划）；
  - 同号不同内容：返回幂等冲突错误，原计划保持不变。
- **并发**：提交、修改、取消、状态迁移在同一互斥区内“检查 + 落库”串行完成，
  多辆车并发争用同一时段时，只有仍满足全部容量约束的计划组合能提交成功。
- **抵达前修改/取消**：
  - 修改是**原子替换**：先按旧计划之外的占用计算新分配，成功则一次性替换，
    失败则旧计划与旧占用原封不动；
  - 取消立即释放全部占用；重复取消、取消不存在的计划返回状态错误；
  - 当前时间一旦越过到达点，计划自动迁移为 `arrived` 终态并锁定，
    修改/取消与“越过到达点”同时发生时，二者在同一锁下竞争，
    容量不会泄漏，也不会被重复释放。

## 计划状态

| 状态 | 含义 |
| --- | --- |
| `active` | 已提交、车辆未抵达，占用容量，可修改或取消 |
| `arrived` | 当前时间已越过到达点，占用保留但不可再修改/取消（终态） |
| `cancelled` | 抵达前被取消，占用为零（终态） |

## 容量临时下降（削减）调整

当站点可用功率在某段时间临时下降（容量事件 `CurtailmentEvent{StationID, Start, End, PowerW}`）
时，系统以**两阶段**方式处理：先出一份可确认的调整方案，确认后才真正落库。

### 预约属性

- `Priority int32`：优先级，**数值越大越受保护**。容量不足时低优先级预约先被位移，
  高优先级预约尽量维持原安排。
- `FixedPower bool`：固定功率预约。削减时其功率分配**完全不允许降低**，
  占用被当作不可移动的障碍物。
- 已抵达（`arrived`）的预约同样锁死，不参与削减。

### 调整规则

1. **固定/已抵达不可降**：固定功率预约与已抵达预约的占用在事件窗口内完整保留。
   若其占用本身已高于降容后容量，则整份方案无法生成（`capacity` 错误）。
2. **可调整预约不低于最低需求**：其余 `active` 非固定预约可以调整，但调整后
   全程交付能量仍必须达到其 `MinEnergy`。被挤出事件窗口的功率允许**转移**到该预约
   在场期内、窗口之外的空闲时段。
3. **按优先级 + 最低需求出方案**：
   - 先按优先级从高到低（并列时最早离开优先）在事件窗口内尽量保留原分配，
     放不下的部分被挤出；
   - 再按最早离开优先（EDF）把被挤出的缺额贪心回补到各自在场期内的空闲时段；
   - 任一笔预约补不回最低需求 → 返回 `capacity`，不出方案、状态不变。
4. **同一事务原子确认**：`ConfirmCurtailment` 在单次原子落库中同时更新
   **站点时段容量**与**所有受影响预约**。确认前逐笔复核版本指纹，任何一笔预约
   被修改/取消、重排范围内出现或消失预约、或站点配置被重配，整份方案即以
   `conflict` 失败，原安排不被部分修改。
5. **版本乐观锁**：方案记录生成时每笔相关预约的 `Revision`；用户的修改、取消会令
   版本递增，从而自动拒绝旧方案。调用方拿到 `conflict` 后应重新 `PrepareCurtailment`。
6. **容量守恒**：确认时按最细时间片独立复核——调整后总占用不超过降容容量，
   且事件窗口内每个时间片的总占用**只减不增**（释放出的窗口容量不会被其他预约
   重新占满），窗口之外占用不增加。

`PrepareCurtailment` 本身**只读**，可安全地重复生成、比较、放弃；只有确认才改状态。

## API 概览

```go
import (
    "context"
    "time"

    fc "github.com/chris64233/go-fleet-charging"
)

store := fc.NewFileStore("data/charging.json") // 或 fc.NewMemoryStore()
svc, err := fc.NewService(store /*, fc.WithClock(myClock)*/)

// 1) 配置站点：两个半开时段的可用功率
svc.ConfigureStation(ctx, fc.StationConfig{
    StationID: "ST-1",
    Segments: []fc.Segment{
        {Start: t10, End: t11, PowerW: 100_000}, // 10:00–11:00，100 kW
        {Start: t11, End: t12, PowerW: 80_000},  // 11:00–12:00，80 kW
    },
})

// 2) 提交计划（request_id 幂等）
plan, err := svc.SubmitPlan(ctx, fc.ChargeRequest{
    RequestID:    "req-20260101-0001",
    StationID:    "ST-1",
    VehicleID:    "VH-7",
    Arrival:      t10,
    Departure:    t12,
    MinEnergyUWh: 50_000_000_000, // 50 kWh
    MaxPowerW:    100_000,        // 单车功率上限 100 kW
})

// 3) 抵达前原子修改（保持同一 request_id）
svc.ModifyPlan(ctx, "req-20260101-0001", fc.PlanModification{ ... })

// 4) 抵达前取消（释放全部占用）
svc.CancelPlan(ctx, "req-20260101-0001")

// 5) 查询单计划 / 逐时段占用
p, _ := svc.GetPlan(ctx, "req-20260101-0001")
rows, _ := svc.Occupancy(ctx, "ST-1", t10, t12)
// rows: [{Start,End, CapacityW, ReservedW, AvailableW} ...]
// 行边界 = 配置时段边界 ∪ 各计划到达/离开边界，保证每行内占用恒定

// 6) 站点可用功率临时下降：先出方案，再确认
plan, err := svc.PrepareCurtailment(ctx, fc.CurtailmentEvent{
    StationID: "ST-1",
    Start:    t10,
    End:      t11,
    PowerW:   60_000, // 该时段容量临时降到 60 kW
})
// plan.Adjustments[i]: {RequestID, Revision, Priority, FixedPower, OldAllocation, NewAllocation}
changed, err := svc.ConfirmCurtailment(ctx, plan) // 原子更新容量 + 全部受影响预约
// 若生成方案后有预约被修改/取消，err 的 Kind == fc.KindConflict，需重新出方案
```

重新配置站点时，若新配置会使任何既有有效计划超额，返回容量错误且旧配置保持不变。

## 持久化

- `MemoryStore`：进程内存储，适合测试。
- `FileStore`：单个 JSON 文件；写入采用“临时文件 + 原子 rename”，
  崩溃时不会出现半截文件。重启后站点配置、计划、占用、幂等记录全部恢复，
  容量约束继续生效。
- 也可实现 `Store` 接口（`Load/Save`）接入数据库；`Save` 要求整体原子替换。

## 错误分类

所有业务错误均为 `*fc.Error`，按 `Kind` 区分，可用 `fc.KindOf(err)` 取类别，
或用 `errors.Is(err, fc.ErrCapacity)` 等哨兵按类别匹配：

| Kind | 触发场景 |
| --- | --- |
| `parameter` | 空 ID、非正能量/负功率、未知站点、配置时段重叠/乱序、查询区间非法 |
| `capacity` | 剩余容量无法在离开前交付最低电量；降配会击穿既有占用；削减后无法把可调整预约全部转移并满足最低需求 |
| `time` | 到达不早于离开、到达时间已过、窗口未被已配置供电时段完整覆盖；削减时段反向 |
| `state` | 计划不存在、重复取消、已取消/已抵达后再修改或取消 |
| `idempotency` | 同一 `request_id` 提交了内容不同的请求 |
| `conflict` | 削减方案生成后，相关预约版本或站点容量已变化，旧方案失效（乐观并发冲突） |

## 分配算法

把配置时段边界与窗口边界（以及占用查询时的计划边界）合并成互不重叠的时间片，
逐片求 `剩余功率 = 站点容量 − 其他有效计划占用`；随后按时间从早到晚贪心填充：

1. 当前片可给功率 `min(剩余功率, 单车功率上限)`；
2. 若整片用完仍不够，取整片功率；
3. 若该片足以补足缺口，只取 `ceil(剩余功量 / 本片时长)` 的最小整数功率；
4. 全部时间片用尽仍不足 → 返回容量错误，不写入任何占用。

贪心在“功率上限为常数、可中途任意改变功率”的模型下是最优的：只要存在可行分配，
最早填充策略就一定能找到。

## 容量削减重分配算法

容量事件只改变一个时间窗口内的容量，但可调整预约可能跨越窗口内外。重排范围取
“事件窗口 ∪ 全部可调整预约在场区间”的并集，按“事件边界 ∪ 站点时段边界 ∪
各预约到达/离开/分配边界”切成容量与占用均为常数的最细时间片。预约分两类：

- **不可移动障碍物**：固定功率预约、已抵达预约，以及只落在外溢时段的第三方预约；
- **可调整预约**：窗口内 active 且非固定的预约。

随后两步确定每笔可调整预约的新功率：

1. **按优先级保留**：优先级高者（并列时最早离开）先在原时间片保留原功率，
   受保护占用先行扣除、时间片放不下的部分被“挤出”。高优先级因此几乎不动。
2. **EDF 回补缺额**：被挤出的预约按最早离开优先，把缺额贪心补到其在场期内
   任意空闲片；回补在事件窗口内还受“该片可调整占用不得超过原占用”的约束，
   保证窗口内释放的容量不会被重新占满。

可行性条件：每笔预约最终功量 ≥ 其最低所需功量；否则返回 `capacity`，不出方案。
确认阶段不直接信任方案，而是按当前快照**独立重建**最细时间片，重新校验
容量上限、窗口守恒与每笔最低需求，再与版本指纹一起通过后才提交。
